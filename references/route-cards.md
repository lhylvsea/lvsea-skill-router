# 方案卡协议

当多个 Skill 或短流水线会产生明显不同的结果时，先给方案卡，不要直接消耗完整制作时间。

## 什么时候给方案卡

需要给方案卡：

- 交付物有两个以上互斥方向，例如 `.pptx`、HTML、图片或 MP4；
- 同一份材料可以做成不同视觉语言，例如数据报告、实况卡、横屏视频或竖屏口播；
- 用户明确要求“给我几个方向”“让我选”“先看效果”；
- 路由置信度不足，且单纯问一个 Skill 名称不能解决歧义。

不需要给方案卡：

- 用户已经明确指定 Skill、格式和效果；
- 只有一条明显符合交付物和边界的路线；
- 用户明确说“按你推荐直接执行”。

## 方案卡格式

```markdown
## 推荐方案 A｜<短名称>

- Skill 组合：`<skill-a>` → `<skill-b>` → `<skill-c>`
- 交付物：<文件、页面、视频、报告或操作结果>
- 预期效果：<视觉、交互、叙事或工程效果>
- 适合：<受众、平台、使用场景>
- 优点：<最重要的 1–3 点>
- 限制：<时长、格式、依赖、授权、可维护性或质量边界>
- 预览：<首屏、关键帧、3–10 秒样片、最小 Demo 或测试计划>
- 验收：<完成后如何证明不是只生成了配置>

## 备选方案 B｜<短名称>
...

## 备选方案 C｜<短名称>
...

➡️ 推荐选择：A，因为 <与用户目标最直接的理由>。
请回复 `A`、`B`、`C`，或说“按推荐直接做”。
```

方案之间必须在制作路线、交付物、信息组织或观看体验上有实质差异；只换配色、标题或背景不算不同方案。

## 组合原则

一个组合最多包含三个职责清楚的阶段：

1. 输入/事实阶段：读取、核验、分析、转录或提取素材；
2. 设计/制作阶段：写作、页面、图像、动画、视频或代码实现；
3. 交付/验收阶段：导出、测试、字幕、媒体 QA、打包或发布准备。

不要把同一阶段的多个近似 Skill 全部加载。若候选只是替代关系，应作为方案卡选项，而不是并行调用。

## 不同任务的预览

预览应与实际路线同构：网页看截图和交互，代码看最小运行样例和测试，视觉任务看风格帧，视频看关键帧或短样片，报告看首屏和核心结论。预览不是最终质量证明，最终交付仍需单独验证。
